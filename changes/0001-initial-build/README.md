# 初回構築

IPA 公開のプロジェクトマネージャ試験（PM）午前Ⅱを、1問ずつ解く静的サイトを作り、GitHub Pages へ公開する。画面は [system-arch-training](https://github.com/rabut001/system-arch-training) を引き継ぎ、問題・正解・解説のデータを新たに作る。

## 現在地

フェーズ0（土台）とフェーズ1（令和7年度秋期）は終わり、利用者のレビューを待っている。令和7年度秋期は問題文25問・解説100肢がすべて `確認済み` である。

フェーズ2のデータ作成は終わった。17回すべてで、問題文425問・解説1700肢が `確認済み` である。平成28年度春期 問2 は解答例で正解が無いので、`answer` を `null` にし、画面ではどの肢も正解として数える（`docs/spec.md` に追記済み）。`npm run check`（データ検証、型チェック、ビルド）は通っている。

画面での確認（Playwright）も済んだ。新しい16回の400問すべてで、画像の表示、キー操作による選択と結果確認、正誤と解説の表示、正解数、再読み込み後の保持を確かめた。ほかに、正解の無い平成28年度春期 問2、誤答、一括採点、クリア、存在しない回、360px 幅、ダークモードを確かめ、横のはみ出しやスクリプトのエラーは無かった。360px 幅で結果を出すと、問題画像の欄が約 100px まで縮む。これは令和7年度秋期でも同じで、画面の配分によるものである。利用者は、基本設計上やむを得ないとして、現状のままでよいと判断した。

次は、利用者にフェーズ1・2の画面と解説を見てもらう。そのあとフェーズ3（公開）に進む。

`.claude/agents/` のサブエージェントは、定義を置いたあとに起動したセッションから使える。それより前に起動したセッションでは、汎用のサブエージェントに定義ファイルを読ませて同じ役割をさせる。

`tools/devc.sh` は開発コンテナに 5173 番を割り当てるので、ほかのプロジェクトのコンテナがそのポートを使っていると起動できない。そのときは、同じイメージを `docker run --rm` でポートなしに起動して、検証やビルドを行う。

### フェーズ2で分かったこと

- 400問のうち約90問は、ほかの回と肢が同じか、ほぼ同じだった。解説は確認済みの回の文を使い回し、出典の回を作成側のコメントに書いた。使い回すときは、設問文の細かな違い（単位、工程名、肢の並び、略称だけの肢など）で解説が合わなくなっていないかを、作成側とレビュー側の両方で確かめた。
- ある回のレビューで文の誤りが見つかったら、同じ文を使った回も合わせて直し、再レビューにかけた。
- 長さの注記（200字を超える理由）は、文を直して200字を下回ったあとも残りやすい。コメントを書いたあとに実際の字数と照らす。
- レビューは一次資料で確かめられないことがある（PMBOK ガイドの原文、JIS の本文など）。その場合は、断定を避けた書き方なら通している。

### フェーズ1で分かったこと

- 解説のレビューで100肢中6肢が `要見直し` になり、1回の直しで解消した。手順と観点は変えずに残り16回へ進める。
- 法令は出題後に改正されることがある（下請法は2026年1月施行の改正で中小受託取引適正化法になった）。正誤は出題時点の法令で判断し、改正があれば短く触れる。観点5にこれを足した。
- `tools/cut.py` は、OCR が「問」を「癌」「則」と読む回があった。実際に出た読み違いだけを足した。25問にならなければ止まるが、25問になっても読み違いと読み落としが重なる恐れはあるので、問題文を起こすときに全画像の先頭の問番号を確かめる。

## 目的

PM 午前Ⅱの過去問 17回・425問を、スマホと PC のブラウザで解けるようにする。解説は学習用に作り、誤りの肢がなぜ誤りかまで分かるものにする。

## 決めたこと

- 対象は午前Ⅱだけ。IPA の過去問題ページにある 17 回（平成21〜31年度春期、平成23年度特別、令和2年度10月、令和3〜7年度秋期）、各25問。
- 画面と操作は参照元を引き継ぐ。参照元の後付けの高さ合わせ（`previousLayout` による計測）は持ち込まず、最終形のレイアウトだけを使う。
- 参照元に加えるのは次の二つだけ。
  - PC のキーボード操作（1〜4 でア〜エ、Enter で結果を確認、← → で前へ・次へ）
  - ダークモード（OS の設定に従う。切り替えボタンは置かない）
- 解説を肢ごとのデータにする案、一覧に進捗を出す案は採らない。
- IPA の PDF はコミットしない。`tools/fetch.py` が `.cache/pdf/` へ取得し、URL と SHA-256 を `content/sources.json` に残す。
- 問題画像は WebP にする。
- 開発は開発コンテナで行う。Claude Code はホスト（WSL）で動かし、Node.js と Python のコマンドは `tools/devc.sh` でコンテナの中で実行する。
- 問題文の起こしと解説の作成はメインのセッションが行い、レビューは `.claude/agents/` のレビュー専用サブエージェントが行う。作った手番で `確認済み` にしない。
- 会話は `chat-exports/` に Markdown で書き出し、GitHub に載せる。システムの付加情報、思考、ツールの出力は含めず、メールアドレスは伏せる。
- 公開先は GitHub リポジトリ `project-manager-training-2` の Pages、公開パスは `/project-manager-training-2/`。

## 今回の仕様に含めないもの

- 解説の肢ごとのデータ化、一覧の進捗表示、PWA。

## 手順

### フェーズ0 土台

1. 開発コンテナ、`tools/devc.sh` を作り、コンテナで Node.js と Python が動くことを確かめる。
2. `docs/spec.md`、`CLAUDE.md`、`README.md` を書く。
3. 参照元の画面を `app/` へ移植し、PM 用に直す。キーボード操作とダークモードを足す。
4. `tools/` の取得、切り出し、正解抽出、検証を作る。
5. `.claude/`（権限、hook、サブエージェント、スキル）と CI を作る。

### フェーズ1 試行（令和7年度秋期）

1. PDF を取得し、25問を切り出し、正解を入れる。切り出しを画像で確かめる。
2. 問題文を起こす（下の「問題文」のループ）。
3. 解説を作る（下の「解説」のループ）。
4. 画面で通して確認する。手順や観点に問題があれば、この文書を直してから次へ進む。

### フェーズ2 残り16回

### フェーズ3 公開

## 問題文

各問に `stem`、`choices`、`visuals` を足す（形式は `docs/spec.md` の「問題データ」）。問題画像から起こし、画像と照合してから `確認済み` にする。図そのものは文字にしない。表は Markdown の表にする。セルの結合や、一つのセルの中の複数行は、結合している範囲を文で補う。

状態は `未着手` → `抽出済み` →（`要見直し` → `抽出済み`）→ `確認済み`。

観点:

1. `stem` が、図と表以外の設問文と一致する。
2. `choices` のア〜エが、画像の各肢と一致する。肢の取り違えがない。
3. 表は Markdown の表にして `stem` または `choices` に含め、`visuals` に `table` を入れている。
4. 図・グラフは文字にせず `visuals` に `figure`、図でも表でもない画像は `image`。該当がなければ空配列。
5. `no`、`answer`、`image` を変えていない。

折り返しの改行は、文のつながりが分かる形に詰めてよい。句読点と用語の文字は画像に合わせる。

表記の取り決め（フェーズ2のレビューで足した）:

- 英字と数字の全角・半角は画像に合わせる。画像で区別できないときは、同じ問の中でそろえる。回をまたいでそろえることは求めない。
- 肢が表の一行のとき（組合せを選ぶ問など）は、肢ごとに見出し行付きの1行の Markdown の表にする。「列名：値」の文にしない。
- 表の外にある「単位 人」などは、画像どおり括弧を付けずに書く。
- ルビは省く。

## 解説

肢ごとに状態を持つ。状態は `未着手` → `作成済み` →（`要見直し` → `作成済み`）→ `確認済み`。一つの `explanation` に4肢の文が入るので、`要見直し` を直すときはその肢の文だけを変える。ほかの肢の文まで変えたら、その肢も `作成済み` に戻す。

観点:

1. 問題文の言い換えで終わらせない。用語の意味、仕組み、背景、具体例のうち、正誤の理由に必要なものを書く。問題文に書いてあることや、問題文から容易に想像できる説明は繰り返さない。問題と関係のない事項は書かない。
2. 各肢に対応する一般的な用語、手法、規格、契約形態、理論があれば特定し、特徴や仕組みを書く。肢の本文が用語の名前だけのときは、その意味を短く書く。意味が問題文や肢の本文にすでにあるときは、名前を特定するだけにする。
3. 肢全体に対応する一般的な概念がなければ、その旨を書く。一部が既存の概念に似ているときは、類似点と相違点を書く。
4. 誤りの肢は、どの記述が、どの概念のどの特徴と食い違うかを書く。計算で値が一つに定まる問は、正解の計算だけを書き、誤答の解説は書かない。最も大きい・小さいものを選ぶ問は、各肢の結果を書くか、式にして最大または最小を求める。
5. 用語、規格、法令、契約の説明が正確である。似た概念を混同しない。一般的な傾向を例外のない規則として書かない。PMBOK ガイドの版（第6版の知識エリア・プロセス群と、第7版の原理・パフォーマンス領域）や JIS Q 21500 / ISO 21502 など、版や規格で用語が違うときは、問題がどれに拠っているかを踏まえる。法令は出題時点のもので正誤を判断し、その後に改正があれば短く触れる。根拠を確認できないことは断定しない。
6. 正解と矛盾しない。正解の肢を最初に示す。`answer` が `null` の問（問題として成立しない問）は、成立しない理由が分かればそれを書き、分からなければ断定せず、各肢の内容を説明する。
7. 長さは全体でおおむね 80〜200 字。超えるときは、作成側がコメントに理由を書き、レビュー側が妥当かを確かめる。肢が名前だけで意味が問題文に無いとき、各肢の結果を比べるときは、その旨を理由にしてよい。

見本（参照元の問題。この文をそのまま流用しない）:

> ラボ契約は、一定以上の発注を約束する代わりに、スキルや人数の基準を満たす要員をベンダーが確保する契約である。イが正解である。アの「担当者の指名」と「直接の指揮命令」を両立する契約形態は、一般的なものでは見当たらない。紹介予定派遣は該当するが、あまり一般的ではない。ウはレベニューシェアの説明である。エは実稼働だけの精算で、通常一定以上の発注が前提となるラボ契約には一致しない。

## チェックリスト

回ごとに `checklist/<回の id>.json` を置く。`content/` には置かない（サイトへ出さない）。

```json
{
  "examId": "2025-r07-aki",
  "questions": [
    {
      "no": 1,
      "text": { "status": "確認済み", "comments": [{ "role": "作成", "text": "…" }] },
      "explanation": {
        "ア": { "status": "作成済み", "comments": [] },
        "イ": { "status": "作成済み", "comments": [] },
        "ウ": { "status": "作成済み", "comments": [] },
        "エ": { "status": "作成済み", "comments": [] }
      }
    }
  ]
}
```

`role` は `作成` または `レビュー`。コメントは追記し、過去の文は消さない。作成側は、図・表の判断、読みに迷った点、断定を避けた点、長くした理由を書く。レビュー側は、`要見直し` にするとき観点の番号と理由を書く。

## 確認

- `tools/devc.sh npm run check` が通る（データ検証、型チェック、ビルド）。
- 17回すべてのチェックリストが、問題文・解説とも `確認済み`。
- 狭い幅（360px 程度）と広い幅で、一覧と演習画面を通して操作できる。ページが横にはみ出さない。
- キーボード操作、ダークモード、再読み込み後の進捗、存在しない回の URL、`404.html` からの直接表示。
- 公開先で一覧と各回が開ける。PDF が成果物に入っていない。
